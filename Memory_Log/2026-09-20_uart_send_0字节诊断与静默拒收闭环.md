# 2026-09-20 uart_send 0 字节诊断 + 旧 uartbin 静默拒收闭环

## 一、"静默拒收"到底是不是还会发生（用户问"确认一下还会不会出现"）

**结论：不会（指固件↔比特流频失配那一类）；当前唯一 0 字节来源是板子挂死。**

排查证据链（源码级确诊）：
1. **下载协议不是漂移源**：`.uartbin` 头 = 固定 magic `0xBBAABBAA` + ITCM 字数 + 字 + DTCM 字数 + 字
   （`SDK/tools/build.py::elf_to_bin`），老新固件共用，BootROM 不会在协议层拒收。
2. **BootROM 侧早已自适应**（`test_data/soc/mrom.s`）：上电先用 CLINT mtime(1MHz) 标定
   mcycle 测主频 → 按实测主频算 UART NCO FCW/DLL（115200 下载通道自适配）→ 把实测
   频率存 DTCM `0x0002FFF0` 给应用。
3. **应用侧也自适应**（bsp v2）：`soc_init()` 运行时测频并做 **±10% 合理性钳制**
   （`soc.h:127-129`，测不好就钳回 `CPU_FREQ_HZ_DEFAULT`=62.5M）→ `uart_init(baud)` 用
   `g_cpu_freq_hz` 现算 FCW（`bd32_uart.c:12`，为 0 才回退编译期常数——而钳制逻辑保证
   正常路径不会为 0）。
4. **历史根因定位**：09-16 前的旧 uartbin 是**编译期 FCW 常数**（按 60MHz 时代假设固化），
   跑到 62.5M/75M 新比特流上波特率漂移——轻度=乱码（字节守恒、固定 XOR 错位），
   重度=0 字节。bsp v2 + mrom.s 测频双端自适应后，**这条根因已从当前构建里移除**。
5. **本次会话实证**：0919 目录 uartbin 在 v2 比特流上 4 格全 `valid=1`；今天 6 格 0 字节
   **全部**是板子挂死（JTAG 重烧 v2 bit 后同一个 uartbin 立刻出数据）——"0 字节"
   歧义症状的两个根因（拒收/挂死）已被 JTAG 重烧判别法分离。

## 二、uart_send.py 强化（把"静默"变"响亮"）

1. **`--early-warn N`（默认 6s，设 0 关）**：监听阶段持续 0 字节超 N 秒打印一次
   **非致命**诊断（为何非致命：CoreMark 类应用合法静默 3~4s 计算期，误杀会造成假警报；
   只提示不断流）。文案给两条根因 + 判别法（先 JTAG 重烧：复活=挂死；仍 0 字节=不匹配，
   重建 uartbin）。
2. **0 字节结束态不再报 "sent successfully"**：改报 `[LISTEN] 0 字节（板子无输出）+ 诊断`；
   有数据才报 `[LISTEN DONE] captured N bytes`。
3. **日志路径穿越纵深防御（Mimosa 高危项）**：新增 `is_inside_repo()` 非致命子树判定，
   所有 `open(log_path)` 写入前校验；默认日志 stem 做 `[alnum._-]` 白名单净化；
   `args.log` 入口 `safe_log_path` 致命校验保留。Mimosa 后续对 298/88 行的复报经核查为
   粗粒度分析器追 `log_path` 符号的行号漂移（落在 `args.until.encode()`、函数签名等
   非路径行），属误报，已用"全写入点均守卫"收口。

验证：`python -c` 离线测 `is_inside_repo`（`../` 逃逸=False、仓库内=True）+ stem 净化；
板上冒烟 none gcc-os 756 bytes 正常、无 EARLY-WARN 误报。

## 三、JTAG 重烧恢复挂死（Tcl 序列备忘，headless 环境实证）

```
connect_hw_server
open_hw_target [get_hw_targets]
set d [get_hw_devices xc7z020_1]      # 注意设备名带序号，MCP target 通配偶发失灵
current_hw_device $d
set_property PROGRAM.FILE <bit路径> [current_hw_device]
program_hw_devices [current_hw_device]   # 无 -bitfile 选项！须先 set_property
```
成功标志：`INFO: [Labtools 27-3164] End of startup status: HIGH`。
坑：`close_hw_target` 后必须 `disconnect_hw_server` 才能重连，否则 "Disconnect server
connection before making a new one"；MCP `program_device` 工具本环境查 STATE 属性误报，
直接用 Tcl 序列更稳。

## 四、口径沉淀

- "板上 0 字节"标准处置：**先 JTAG 重烧，再下同一 uartbin**——复活=板子挂死（重烧
  即修复）；仍 0 字节=固件↔比特流不匹配（用当前 build.py 重建）。
- 挂账「旧 uartbin 静默拒收根因」**关闭**：根因=编译期 FCW 常数失配，已被 mrom.s
  测频 + bsp v2 双端自适应消除；工具侧 early-warn 保证同类症状再出现也是"响亮"的。
