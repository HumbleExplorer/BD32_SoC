# 2026-09-20 取指连续性三件套——formal 反例解剖、板上 A/B 与心得

**commit 1eb11ee**（BTB 半字混叠 + req_fwd 预取前推 + Zcmp capture 恢复基准），比特流
`bd32_board_top_postroute.bit`（WNS +0.014 全 MET），板上验证收口：RT-Thread 24841 字节
t1/t2 零 SERR + CoreMark full-llvm-Os 复测与 A/B 数据逐位一致（ticks 差 10 拍≈4ppm、
fetch 停顿 8,732,815 完全相同）——不同布线种子下结果可复现。

## 一、三个修复

1. **BTB 半字混叠**：index/tag 均弃 PC bit1，跨字 jal 与对齐 PC 折进同一条目 → 永久
   miss、每次 EX 重定向罚 ~3 拍。修：index 扩 pc[8:1]，tag 保持 pc[15:9] 自然排除。
2. **req_fwd 预取前推**：`req_fwd = refill_now | (can_issue & unaligned32 & next_ready
   & ~crossing)`，refill 消费拍请求指针当拍 +4。逻辑上第二项恒为 0（unaligned32 蕴含
   crossing），实际生效的就是 refill_now——但保留它作为防御性意图表达。
3. **Zcmp capture 恢复基准**（fml_a_window_pair 反例定位）：capture 收尾旧写法
   `restore_req_addr <= fetch_addr` 隐含"窗口空时 fetch_addr 与活 req_addr 锁步"，
   req_fwd 打破锁步后恢复出落后 2 字的指针。修：按恢复态选路——持窗口字时
   `窗口字+4`，无窗口字以活 req_addr 为基准。

## 二、formal 反例解剖方法（本轮最大心得）

abc pdr 的 FAIL 只给 Output 序号，**按位序猜断言名极易猜错**（本案 freeze 与
window_pair 混了一轮、连加三重豁免无效）。标准流程：

1. pdr 反例的 yw 只含自由输入、无内部状态；Windows 下 `yosys-smtbmc --yw` 还常因
   信号名不匹配崩掉拿不到 VCD。
2. 正确姿势：按 sby 的 [script] 手动展开（补 `async2sync; dffunmap`）→
   `write_smt2 -wires` → 裸跑 `yosys-smtbmc -s yices -t N --dump-vcd`——既报断言
   真名又带全部内部信号。
3. **豁免连加压不住 = 语义/根因判断错了**，不是边角时序。转去看别的断言。
4. VCD 帧解剖判读：违约帧向前追 restore 寄存器的锁存拍，对拍"锁存值 vs 违约帧
   活值"即可区分"恢复数据错"与"锁存基准过时"——本案属后者（冻结保住了活指针，
   救不了陈旧锁存值）。

## 三、上板工具链坑（三条都是这次踩出来的）

- **uart_send.py 默认 `--idle-timeout 3s`**：CoreMark banner 后有 2.9~3.5s 静默
  计算期，listener 提前退场只抓 22 字节 banner，表象酷似"挂死/输出丢失"。判据：
  JTAG halt 读 pc 落在 _start 尾部 `j .`（main 已完成）+ LSR=0x60 健康。
  **CoreMark 类长静默应用必须 `--idle-timeout 30 --timeout 300`**。
- **旧 ext uartbin 被新比特流静默拒收**（0 字节无 banner）：必须用当前 build.py
  重建；重建后 Total inst 与基线差 0.001%（同指令流），根因待查但不阻塞。
- **时序收敛流程**：impl 布线后 WNS 常负 0.05~0.3ns 且**不自动跑 postroute
  physopt**——`open_checkpoint routed.dcp; phys_opt_design -directive
  AggressiveExplore` 定向收尾稳定可解（两轮分别 -0.283→+0.000、-0.255→+0.014），
  再 `write_bitstream -force` 直出。Performance_Explore 反而更差（-0.283），勿用。
  REQ P-1839/ZPS7-1 是历次都有已知警告。

## 四、板上 A/B 结论（62.5MHz，500 轮，重建固件 vs 09-18 基线）

| 配置 | ticks 变化 | fetch 停顿变化 |
|---|---|---|
| none gcc-O2 | +1.5%（噪声底） | 0 |
| none llvm-Os | +1.7%（噪声底） | 0 |
| C gcc-O2 | **-5.1%** | -35%（37.9M→24.6M） |
| full gcc-O2 | **-4.7%** | -46% |
| C llvm-Os | **-3.3%** | -39% |
| full llvm-Os | **-4.2%** | **-53%**（18.7M→8.7M） |

none 配置 d_inst=0.00%（同指令流），其 +1.5~1.7% 即重建布局漂移噪声底；校准后
C 配置真实收益 ≈ -5%~-7%。**"RV32C 亏性能"口径更新：LLVM Os 全扩展净损失
-7% → 约 -2.5%**。fetch 停顿砍半是 req_fwd 消除跨字停顿的直接板级证据。

## 五、架构心得（与 Ibex 对比沉淀，详见会话记录）

- BD32 单字窗口 + 幂等重复请求 vs Ibex 3 深 FIFO + 2 项在途跟踪：**深度跟着存储
  延迟走**——ITCM 恒定 1 拍读延迟不需要 FIFO；Ibex 的 FIFO 头注释明说是为"切断
  到 instruction cache 的长关键路径"。我们的组合 pc mux 直达 BRAM 地址口正是全
  设计最难时序路径（两轮 physopt 日志里 pc[14]/ITCM ADDRARDADDR 反复出现）。
- 三处异曲同工：空窗旁路（refill_now vs valid_q[0]?rdata_q[0]:in_rdata_i）、跨字
  拼接（{w_new[15:0],cur_w[31:16]} vs {in_rdata_i[15:0],rdata[31:16]}，逐位相同）、
  发射门控（next_ready vs valid_unaligned）——独立收敛到同一合同，说明该合同值得
  formal 断言。
- "pc mux 后加一级寄存"预案 = 流水图变 6 级但非 6 级改造：无新冒险域（旧地址数据
  被 req_addr 配对自然丢弃）、吞吐不变、取指延迟+1、重定向惩罚+1；代价是簿记
  1 深→2 深（正是 Ibex rdata_outstanding 的存在理由）。触发条件：频率上调或该
  路径再度违约。
